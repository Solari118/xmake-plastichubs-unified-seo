# Delivery And Variation Framework

Use this reference for batches of related service, finishing, material, industry, or solution pages and for preview/Word delivery.

## Architecture Selection

Choose one primary pattern from the buyer task:

1. Suitability decision: fit / not-fit criteria, constraints, and RFQ inputs.
2. Failure diagnosis: symptom, mechanism, corrective action, and prevention.
3. Specification and acceptance: target, test method, tolerance, and approval path.
4. Option comparison: shared criteria, tradeoffs, and selection result.
5. Process workflow: inputs, controls, inspection, and handoff risks.
6. Application-led: use condition, material/process choice, failure risk, and verification.
7. Case-led: initial problem, engineering decision, result boundary, and transferable lesson.
8. Myth/risk correction: common assumption, why it fails, decision rule, and next action.

Do not name the pattern in public copy. A page may use secondary modules, but one pattern must control the reasoning order.

## Batch Diversity Matrix

Before drafting a sibling page, record privately:

- architecture pattern
- hero consequence
- first decision aid
- dominant evidence form: table, checklist, process map, failure matrix, example, or specification block
- CTA position
- optional modules omitted
- closing form

Do not reuse the same combination for consecutive pages unless the search intent makes the repetition necessary. Structural variation must not remove essential buyer information.

## Redundancy Gate

- Give each H2 one reader job.
- Merge “specifications,” “selection guide,” and “when to choose” modules when they repeat the same criteria.
- Do not restate advantages in the FAQ or CTA.
- Compare the draft with at least the previous two sibling pages when they are available; flag repeated headings, paragraph skeletons, trust bullets, and CTA sentences.

## Review And Preview Delivery

- `Bilingual Review Draft`: stacked Markdown, Chinese first and English second, no raw layout HTML.
- `Paginated Preview`: PDF unless another format is requested. Render every page and inspect clipping, fonts, tables, headings, links, and bilingual punctuation.
- `Publish-ready English`: content approved and final-Audit conditions satisfied.
- `WordPress-ready`: approved copy plus metadata, heading hierarchy, internal links, image requirements, and schema recommendation.
- `Word-ready`: post-approval `.docx` using the requested style reference. Render and inspect every page before claiming visual QA.

If rendering is unavailable, state `Structural QA only — visual QA not completed` and do not label the artifact Word-ready.

## Correction Persistence

When the user corrects wording, layout, route, or display behavior, update the source artifact and relevant reusable rule before reporting completion. A chat-only correction is incomplete.
